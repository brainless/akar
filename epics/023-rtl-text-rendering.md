**Status:** Research Complete and Verified — Implementation Not Started. Tasks 1-6 (research) are Done. Tasks 7, 9, 10, 12, and 13 are ready for implementation subject to their recorded dependencies; Task 8 is optional non-blocking visual research; Task 11 is a newly discovered editing feature and is explicitly deferred from this epic's first implementation pass. **Goal:** Establish correct rendering and interaction for right-to-left scripts (Arabic, Hebrew, etc.), covering both glyph shaping and direction-aware layout.

**Prerequisite:** Epic 021 is `Status: Done`. Findings from [[022]] (font support) inform this epic — RTL scripts need correctly loaded, fallback-capable fonts before layout direction is even worth testing.

---

## Introduction

RTL is commonly treated as a text-shaping problem, but the shaping half is largely already solved: cosmic-text's shaping backend (rustybuzz) and glyphon already implement the Unicode Bidirectional Algorithm and correct glyph shaping for Arabic/Hebrew scripts at the glyph level. What akar does not yet have is **direction-aware layout** — the property that an entire subtree (icon positions, scroll direction, text alignment, caret movement, selection anchors, component internal padding) mirrors when the surrounding context is RTL.

This is a layout-and-interaction problem more than a rendering problem, and it touches nearly every component in `akar-components` to some degree (icon placement in buttons/badges, scrollbar side, tab bar order, navbar item order, text input caret/selection math). Given the size of that surface, this epic should not try to convert the whole component catalog in one pass — the initial scope should prove the direction model end-to-end on a small number of components before it is rolled out further.

## Research

Initial inputs, to be expanded by the coding agent doing the investigation:

- **Shaping is not the gap; layout is.** Confirm via `~/Projects/glyphon` and cosmic-text's shaping path that bidi reordering and per-run direction are already handled at the glyph level. The investigation should focus on what's missing above that layer, not attempt to reimplement bidi.
- **taffy's RTL support is partial and needs verification.** `~/Projects/taffy` supports `flex-direction: row-reverse`, which can approximate RTL for simple row layouts, but this is not the same as full logical-properties layout (`start`/`end` instead of `left`/`right`, mirrored margins/padding, mirrored `justify-content`). Read taffy's source and its own test suite for what direction/writing-mode support exists versus what would need to live in akar's layout wrapper (`akar-layout`) as a pre/post-processing step.
- **Reference prior art before designing from scratch.** `~/Projects/egui` — check if egui has any RTL support and how it structures direction as a layout concept, since akar's immediate-mode model is close to egui's. `~/Projects/zed/crates/gpui` is a secondary reference for a production wgpu UI's approach, if it has one.
- **A global direction context is the likely shape.** Something like `AkarDirection { Ltr, Rtl }` set on the theme/context (mirroring how the flat `AkarTheme` already works — see `DEVELOP.md` → Theme system) rather than a per-node property, at least for a first version. Per-node direction (mixed-direction documents) is a much larger undertaking and should be an explicit deferral initially.
- **Text editing is a distinct sub-problem.** Epic 018 established `TextEditState { cursor, anchor }` as byte offsets (epics/018, Task 4 — "Shared Selection and Editing Engine") with caret/selection geometry derived from shaped glyphon layout (epics/018, Task 5 — "Selection and Caret Rendering"). For RTL text, "moving right" and "moving forward in the string" are not the same operation — Left/Right arrow key handling, caret geometry, and selection-drag math all need direction awareness. This is likely the highest-value, most self-contained place to prove the direction model, since it's already isolated behind `TextEditState` and shared editing helpers.
- **Component audit needed.** Icon-bearing components (buttons with leading/trailing icons, navbar, tab bar) and scrollable containers (scroll area, virtualized lists) have hard-coded left/right or start-position assumptions that need to be found and cataloged before any mirroring work starts.

### Confirmed findings (source analysis, this investigation pass)

**Shaping-layer bidi is confirmed already solved, at multiple layers, not just "probably".**
- `~/.cargo/registry/src/.../cosmic-text-0.18.2/Cargo.toml:178` depends directly on `unicode-bidi`, and `~/.cargo/registry/src/.../cosmic-text-0.18.2/src/{bidi_para,layout,shape}.rs` all reference it — cosmic-text runs the full UAX#9 bidi algorithm per paragraph, not a partial/heuristic pass.
- `crates/akar-core/src/text_pipeline.rs:332-366` (`caret_x`) and `:368-379` (`glyph_boundary_x`) already read `glyph.level.is_rtl()` per glyph (at `:349`, `:356`, `:374`) to place the caret and selection-span boundaries — this is bidi-level-aware code that predates this epic (added for epic 018's caret/selection geometry, commit `105e6dc "Render shaped text selections and carets"`). It works correctly for glyph-level visual positioning inside a shaped run today.
- `~/.cargo/registry/.../cosmic-text-0.18.2/src/buffer_line.rs:146` documents that `Align: None` (the default) resolves to `Align::Right` for RTL paragraphs and `Align::Left` for LTR ones (confirmed in `shape.rs:2570`: `let align = align.unwrap_or(if self.rtl { Align::Right } else { Align::Left });`). `crates/akar-core/src/text_pipeline.rs:61-97` (`TextPipeline::set_text`) always passes `None` for the alignment argument to `buffer.set_text(..)` (the `None` is at `:92`). **Consequence: a pure-RTL string pushed through `push_text` today already right-aligns itself inside its measured box with no akar-side direction code at all** — confirmed by execution on 2026-08-12, see the review section below — this is a case where "looks correct" is achievable purely by not overriding cosmic-text's default, and should be called out explicitly as *already working* rather than something to build.
- What is *not* solved at this layer: which direction the surrounding layout box, sibling order, and caret movement semantics should use. Bidi solves "how do glyphs order inside one shaped paragraph"; it says nothing about `akar-layout`'s flex order, icon slot order, or arrow-key-to-byte-offset mapping used by `text_edit.rs`.

**taffy's RTL support is more complete than the epic's original hypothesis, not partial.**
- `taffy-0.11.0/src/style/mod.rs:394-400` defines `pub enum Direction { Ltr (default), Rtl }` as a first-class CSS-equivalent style property (`CoreStyle::direction` accessor at `mod.rs:110`, `Style` field at `mod.rs:448`, default `Direction::Ltr` at `mod.rs:595`), separate from `FlexDirection` (`style/flex.rs:108-126`). The correct claim is therefore stronger, not weaker: RTL is not a bolt-on corner of taffy's suite, it is cross-checked against browser output for the whole fixture corpus.

**Prior art is thinner than assumed, and both direction models differ from the epic's global-flag proposal in ways worth noting.**
- `~/Projects/egui`: `epaint::Direction` (`crates/epaint/src/direction.rs`) is a four-way cardinal enum (`LeftToRight | RightToLeft | TopDown | BottomUp`) used as `egui::Layout::main_dir` (`crates/egui/src/layout.rs:104,143,156-158`). It is a **per-`Ui`/per-container parameter the application passes explicitly** (`ui.with_layout(Layout::right_to_left(Align::TOP), ...)`), not a locale/script-driven global flag that mirrors an entire app automatically. egui does not appear to auto-detect RTL from text content or apply it tree-wide.
- egui's text cursor/selection code (`crates/egui/src/text_selection/text_cursor_state.rs`, `crates/epaint/src/text/cursor.rs`) has no `rtl`/bidi-aware arrow-key handling found by search — egui has the same "logical Left/Right key vs. visual direction" gap that akar has (see Task 5). This is useful context: akar would not be behind the closest immediate-mode reference on this specific sub-problem.
- `~/Projects/zed/crates/gpui`: no RTL/direction/writing-mode handling found anywhere in the crate (`Rtl`, `right_to_left`, `is_rtl`, `WritingMode` all zero matches). gpui is not a usable reference for this epic; it defers the problem entirely (or handles it upstream in a way not visible in this checkout).
- Mapping to akar's lifecycle (`DEVELOP.md` → Component lifecycle): egui's per-call `Layout` parameter doesn't map cleanly onto akar's construct/compute/paint split, because akar's `Style` is set once at construct time by `*_layout()` functions and reused across frames — there is no per-frame "layout call" to attach a direction argument to the way egui's immediate `with_layout` closures do. A context-level `AkarDirection`, read once by `*_layout()` functions at construct time (the same phase that already reads `&AkarTheme`), fits akar's existing "flat context, no cascade" model (`DEVELOP.md` → Theme system) much better than egui's per-call model. This confirms — with a concrete mechanism, not just an analogy — the epic's original hypothesis that a context-level flag is the right shape for v1.

**Component audit (Task 4 detail) revealed the actual codebase is a mix of already-neutral, easy-to-fix, and not-yet-existing surfaces** — narrower than the epic's original list of suspects. See Task 4 below for the full breakdown; headline finding: `akar-components/src/button.rs` and `badge.rs` currently have **no icon-slot concept at all** (`grep -n icon button.rs` returns nothing), so "icon placement in buttons/badges" from the epic's original Research list is aspirational, not an existing bug to fix. Likewise `scroll_area.rs` has no scrollbar thumb/track drawing code today (`grep -rl scrollbar akar-components/src` is empty) — "scrollbar side" is not yet an existing surface either.

**Text editing (Task 5 detail) has a confirmed, concrete, cited bug**, not just a hypothesized gap: `crates/akar-components/src/text_input.rs:128-137` (corrected from `128-135`; the `text_input` arms are multi-line and also reset `anchor`) and `textarea.rs:154-157` map `Key::Left` unconditionally to `previous_boundary` (decrease byte offset) and `Key::Right` unconditionally to `next_boundary` (increase byte offset). This is correct only because LTR text happens to have "visually left" and "logically previous" coincide. For pure-RTL text (where cosmic-text right-aligns the paragraph and reorders glyphs, per the bidi finding above), pressing the physical Left arrow key should move the caret to a smaller *visual x* — which is *logically forward* (toward `next_boundary`) for a right-aligned RTL line, not backward. `text_edit.rs`'s `previous_boundary`/`next_boundary` (lines 117-131) operate purely on the `&str` value with zero access to shaped-buffer bidi levels, so they structurally cannot make this distinction today — the fix needs a direction signal to reach `text_edit.rs`, not just a smarter string function.

### Task 12's proposed C ABI shape is wrong; here is the actual pattern

**[read]** `crates/akar-c-api/src/lib.rs`:

- `Layout` is a **private field** of the opaque `AkarCtx` (`:16-22`: `pub struct AkarCtx { core, layout, theme, device, queue }`). No `Layout*` ever crosses the ABI, so the proposed `akar_layout_set_direction(layout, direction)` cannot be written as specified. The established shape is `akar_set_<thing>(ctx, ...)` operating on `ctx.layout` / `ctx.core`.
- Canonical setter to mirror: `akar_set_text_edit_keybindings(ctx: *mut AkarCtx, bindings: AkarTextEditKeybindings) -> bool` (`:1417-1440`) — decode the raw values first, then `let Some(ctx) = (unsafe { ctx.as_mut() }) else { return false };`, then delegate.

- Enums do **not** cross as C enums. The convention is a `#[repr(C)]` one-field wrapper struct plus a `*_from_raw` decoder: see `AkarTextAlign { value: u32 }` (`:38-41`) alongside `AkarFontFamily`/`AkarFontWeight`, and decoders `key_from_raw` (`:1330`), `shortcut_modifiers_from_raw` (`:1348`), `modifiers_from_raw` (`:1368`). New public types must also be added to the `[export] include` list in `crates/akar-c-api/cbindgen.toml`.
- Tests: `crates/akar-c-api/tests/api.rs` is a **Rust** integration test driving the C functions directly via `akar_ctx_mock()` (first use at `api.rs:14`) — headless, no GPU. `tests/text_edit.c` + `tests/c_text_edit.rs` is the actual C-compiled test. ### `collapse_to_start` / `collapse_to_end`: answered

**[read]** Task 10 asked whether these need changing. They do not — but their **call sites** do.

`TextEditState::collapse_to_start` (`text_edit.rs:26-29`) and `collapse_to_end` (`:31-33`) are defined purely logically, as `selection().start` = `min(cursor, anchor)` and `selection().end` = `max(cursor, anchor)` (`:13-15`). That is the correct, direction-free definition and should stay. What is direction-dependent is *which one `Key::Left` should call*: for a right-aligned RTL paragraph, the visually-leftmost edge of a selection is its logically-**later** offset, so under `AkarDirection::Rtl` the `Key::Left` arm must call `collapse_to_end` and the `Key::Right` arm `collapse_to_start`. Keep the state methods logical; swap at the four call sites (`text_input.rs:128,133`, `textarea.rs:154,156`), exactly as the `visual_previous`/`visual_next` swap does for the no-selection arms.

Related, and not previously noted: `Key::Home`/`Key::End` have the same conflation. `text_input.rs:138-145` sets cursor to `0` / `value.len()`, and `textarea.rs:164-169` uses `line_start`/`line_end`. Browsers treat Home/End as *visual* line start/end. Under the v1 whole-value model these would swap too. Recorded as a deferral rather than folded into Task 10, to keep that task's diff small.

Based on Tasks 1-5, this is a concrete proposal for the first implementation pass, following akar's existing conventions (context-level flat config, no cascade, per `DEVELOP.md` → Theme system; construct/compute/paint separation).

**1. `AkarDirection` type and where it lives.**
- Add `pub enum AkarDirection { Ltr, Rtl }` (mirroring `taffy::style::Direction`'s two variants, but as an akar-owned type so `akar-layout`/`akar-components` don't leak `taffy::Direction` across the C ABI boundary — the same reasoning epic 020 used for its akar-owned `FontFamily`/`FontWeight`/`TextAlign`/`TextStyle` types wrapping glyphon internals, so public component APIs never expose glyphon types directly, per `epics/020-component-webpage-sample.md` Task 2 and Design Decisions). **Correction:** an earlier draft of this section cited these as "`AkarTypography`" — no such type exists; `epics/022-font-support.md`'s own Task 1 findings (line 63) already caught and corrected this exact naming error for a different epic, and this draft had reintroduced it. The real types live in `crates/akar-components/src/text_style.rs`. Natural home for `AkarDirection`: `crates/akar-layout/src/lib.rs`, next to `AkarNodeContext` (`lib.rs:18-21`), since it's consumed at `Style` construction time.
- Store the active direction on `Layout` itself (`crates/akar-layout/src/lib.rs:35-41`), as a new field parallel to `screen_origin`/`namespace_id`, with `set_direction`/`direction()` accessors mirroring the existing `set_namespace_id`/`namespace_id()` pattern (`lib.rs:58-64`). Rationale, established in Task 3: every `*_layout()` construction function already takes `&mut Layout`, but not every one uses `&AkarTheme` meaningfully (e.g. `navbar_layout`'s `_theme` parameter is unused, `navbar.rs:32`) — anchoring direction to `Layout` guarantees it's available wherever a `Style` is constructed, without depending on theme plumbing that isn't uniformly used for other purposes. `AkarCore` (`crates/akar-core/src/context.rs:8-21`) is the wrong home for a layout-tree-scoped value — `Layout` and `AkarCore` are separate objects (per the crate boundary table in `AGENTS.md`: `akar-layout` owns the taffy wrapper, `akar-core` owns draw list/input), and `Layout` already carries the other per-tree context (`screen_origin`, `namespace_id`) that direction most resembles.
- Applications set it once via `layout.set_direction(AkarDirection::Rtl)`, analogous to how `text_edit_keybindings` is configured once on `AkarCore` in epic 018 (`epics/018-text-editing-keybindings-and-clipboard.md`'s "Context-Level Keybinding Defaults").

**2. Where it plugs into `akar-layout`.**
- `*_layout()` construction functions (`navbar_layout`, `card_layout`, future `heading_layout`, etc. — per `DEVELOP.md`'s construct/compute/paint model) read `layout.direction()` and set `taffy::Style { direction: direction.into(), ..existing }` on the nodes they construct — a direct `From<AkarDirection> for taffy::style::Direction` impl, no reimplementation of taffy's mirroring logic (per the Task 2 recommendation). This is additive: existing `Style { .. }` literals gain one field.
- Do **not** attempt to retrofit every existing `Style` construction site in one pass — scope the first implementation to the specific nodes exercised by the two proof components below (Task 6 §4), and leave the rest at the `Direction::Ltr` default until proven.

**3. Where it plugs into text editing (`TextEditState` / shared editing engine).**
- `crates/akar-components/src/text_edit.rs`'s `previous_boundary`/`next_boundary` (lines 117-131) need a direction parameter to choose which byte-offset function corresponds to "visually toward smaller x" vs. "visually toward larger x" for a given paragraph. Minimal viable signature change: `pub fn visual_previous(value: &str, position: usize, direction: AkarDirection) -> usize` / `visual_next(...)` that, for v1, treat the *whole value* as one paragraph-level direction (matching this epic's own "global direction, not mixed/per-run" scoping — see Notes for Future Work) — i.e. under `AkarDirection::Rtl`, `visual_previous` calls today's `next_boundary` internally and vice versa. This avoids needing shaped-buffer/bidi-level access inside `akar-components` for v1; true per-run mixed-direction caret movement (reading `TextPipeline`'s per-glyph `level`, as `caret_x`/`glyph_boundary_x` already do in `crates/akar-core/src/text_pipeline.rs:332-379`) is an explicit deferral (§5).
- `text_input.rs:128-137` and `textarea.rs:154-157` change their `Key::Left`/`Key::Right` arms to call `visual_previous`/`visual_next` with a direction obtained from the component's `&Layout` (`layout.direction()`) rather than the current unconditional `previous_boundary`/`next_boundary`.
- `TextEditState` itself (`text_edit.rs:1-5`, `cursor`/`anchor` as byte offsets) does **not** need to change shape — direction only changes which boundary function callers invoke, not the state representation. - **Tooling gotcha 2 — `--dump-frame` writes exactly one frame.** `main.rs:2301-2304` gates on `!self.dump_frame_written`, so a `--script` with several `screenshot` lines still produces a single dump (the first capture frame). Numeric caret verification therefore needs one `--dump-frame` run per state, or a demo change to allow repeated dumps.

## Notes for Future Work

- Mixed-direction (bidi) documents with per-node direction overrides are a substantially larger effort than a single global direction flag and should stay out of scope until the global-direction model is proven.
- Vertical writing modes (CJK vertical text) are unrelated to RTL and are explicitly out of scope for this epic.
- Canvas world-space text (`CanvasPainter`, display-only per `DEVELOP.md`) may need its own direction handling pass separate from layout-based components, since it bypasses `akar-layout` entirely.
- `Key::Home` / `Key::End` are logical (string start/end, or line start/end) rather than visual in both editors (`text_input.rs:138-145`, `textarea.rs:164-169`). Browsers treat them as visual line edges, so they have the same logical-vs-visual conflation as the arrow keys. Deliberately left out of Task 10 to keep that diff small; revisit after the direction model is proven.
- **From epic 022 Task 9 (2026-08-14), the CJK/Arabic render prototype.** Arabic now renders end to end through akar's public font API (`TextPipeline::load_font_bytes` + `FontFamily::Named`) and was screenshot-verified: contextual joining and RTL glyph order are correct at the pixel level, so this epic inherits no shaping defect. Two verification follow-ups came out of it, neither a bug found, both things this epic should confirm rather than assume: (a) the RTL paragraph appears right-aligned because cosmic-text places an RTL run at the right edge of the shaped buffer, while `crates/akar-components/src/paragraph.rs` computes its own `x_offset` treating `TextAlign::Start` as offset 0 — the two agree only while the buffer width equals the node width, so Task 9 (direction-aware `TextAlign::Start`/`End`) must make sure akar's offset math and cosmic-text's run placement do not double-apply when they diverge; (b) a single line mixing LTR and RTL runs was not exercised by that prototype and remains unverified at the pixel level. Reproduce with `cargo run --bin demo-rust -- --component i18n --script examples/demo-rust/scripts/i18n_named_fonts.txt --exit`.
- `taffy::style::Direction` does not inherit down the layout tree. Any future "set direction once, mirror everything" ergonomics in akar has to be implemented by akar (e.g. stamping the value at node-creation time in `Layout`), not inherited from taffy. Recorded here because it is easy to assume CSS-like inheritance and be wrong.
