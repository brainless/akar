# Epic 023: Right-to-Left (RTL) Text and Layout

**Status:** Research Complete — Implementation Not Started (Tasks 1-6 researched below via source analysis, no live render available in this environment; new implementation Tasks 7-13 added for a future agent, none implemented)
**Goal:** Establish correct rendering and interaction for right-to-left scripts (Arabic, Hebrew, etc.), covering both glyph shaping and direction-aware layout.

**Prerequisite:** Epic 021 is `Status: Done`. Findings from [[022]] (font support) inform this epic — RTL scripts need correctly loaded, fallback-capable fonts before layout direction is even worth testing.

---

## Introduction

RTL is commonly treated as a text-shaping problem, but the shaping half is largely already solved: cosmic-text's shaping backend (rustybuzz) and glyphon already implement the Unicode Bidirectional Algorithm and correct glyph shaping for Arabic/Hebrew scripts at the glyph level. What akar does not yet have is **direction-aware layout** — the property that an entire subtree (icon positions, scroll direction, text alignment, caret movement, selection anchors, component internal padding) mirrors when the surrounding context is RTL.

This is a layout-and-interaction problem more than a rendering problem, and it touches nearly every component in `akar-components` to some degree (icon placement in buttons/badges, scrollbar side, tab bar order, navbar item order, text input caret/selection math). Given the size of that surface, this epic should not try to convert the whole component catalog in one pass — the initial scope should prove the direction model end-to-end on a small number of components before it is rolled out further.

## Research

Initial inputs, to be expanded by the coding agent doing the investigation:

- **Shaping is not the gap; layout is.** Confirm via `~/Projects/glyphon` and cosmic-text's shaping path that bidi reordering and per-run direction are already handled at the glyph level. The investigation should focus on what's missing above that layer, not attempt to reimplement bidi.
- **taffy's RTL support is partial and needs verification.** `~/Projects/taffy` supports `flex-direction: row-reverse`, which can approximate RTL for simple row layouts, but this is not the same as full logical-properties layout (`start`/`end` instead of `left`/`right`, mirrored margins/padding, mirrored `justify-content`). Read taffy's source and its own test suite for what direction/writing-mode support exists versus what would need to live in akar's layout wrapper (`akar-layout`) as a pre/post-processing step.
- **Reference prior art before designing from scratch.** `~/Projects/egui` — check if egui has any RTL support and how it structures direction as a layout concept, since akar's immediate-mode model is close to egui's. `~/Projects/zed/crates/gpui` is a secondary reference for a production wgpu UI's approach, if it has one.
- **A global direction context is the likely shape.** Something like `AkarDirection { Ltr, Rtl }` set on the theme/context (mirroring how the flat `AkarTheme` already works — see `DEVELOP.md` → Theme system) rather than a per-node property, at least for a first version. Per-node direction (mixed-direction documents) is a much larger undertaking and should be an explicit deferral initially.
- **Text editing is a distinct sub-problem.** Epic 018 established `TextEditState { cursor, anchor }` as byte offsets (epics/018, Task 4 — "Shared Selection and Editing Engine") with caret/selection geometry derived from shaped glyphon layout (epics/018, Task 5 — "Selection and Caret Rendering"). For RTL text, "moving right" and "moving forward in the string" are not the same operation — Left/Right arrow key handling, caret geometry, and selection-drag math all need direction awareness. This is likely the highest-value, most self-contained place to prove the direction model, since it's already isolated behind `TextEditState` and shared editing helpers.
- **Component audit needed.** Icon-bearing components (buttons with leading/trailing icons, navbar, tab bar) and scrollable containers (scroll area, virtualized lists) have hard-coded left/right or start-position assumptions that need to be found and cataloged before any mirroring work starts.

### Confirmed findings (source analysis, this investigation pass)

**Shaping-layer bidi is confirmed already solved, at multiple layers, not just "probably".**
- `~/.cargo/registry/src/.../cosmic-text-0.18.2/Cargo.toml:178` depends directly on `unicode-bidi`, and `~/.cargo/registry/src/.../cosmic-text-0.18.2/src/{bidi_para,layout,shape}.rs` all reference it — cosmic-text runs the full UAX#9 bidi algorithm per paragraph, not a partial/heuristic pass.
- `crates/akar-core/src/text_pipeline.rs:349-378` (`caret_x`, `glyph_boundary_x`) already reads `glyph.level.is_rtl()` per glyph to place the caret and selection-span boundaries — this is bidi-level-aware code that predates this epic (added for epic 018's caret/selection geometry, commit `105e6dc "Render shaped text selections and carets"`). It works correctly for glyph-level visual positioning inside a shaped run today.
- `~/.cargo/registry/.../cosmic-text-0.18.2/src/buffer_line.rs:146` documents that `Align: None` (the default) resolves to `Align::Right` for RTL paragraphs and `Align::Left` for LTR ones (confirmed in `shape.rs:2570`). `crates/akar-core/src/text_pipeline.rs:87-93` (`TextPipeline::set_text`) always passes `None` for the alignment argument to `buffer.set_text(..)`. **Consequence: a pure-RTL string pushed through `push_text` today already right-aligns itself inside its measured box with no akar-side direction code at all** — this is a case where "looks correct" is achievable purely by not overriding cosmic-text's default, and should be called out explicitly as *already working* rather than something to build.
- What is *not* solved at this layer: which direction the surrounding layout box, sibling order, and caret movement semantics should use. Bidi solves "how do glyphs order inside one shaped paragraph"; it says nothing about `akar-layout`'s flex order, icon slot order, or arrow-key-to-byte-offset mapping used by `text_edit.rs`.

**taffy's RTL support is more complete than the epic's original hypothesis, not partial.**
- `~/Projects/taffy/src/style/mod.rs:388-399` defines `pub enum Direction { Ltr (default), Rtl }` as a first-class CSS-equivalent style property (`direction` in `CoreStyle`, field at `mod.rs:448`, default `Direction::Ltr` at `mod.rs:595`), separate from `FlexDirection`.
- It is threaded through the actual compute paths, not just declared: `compute/flexbox.rs:442` reads `style.direction()` and reverses main-axis order for `FlexDirection::Row` under RTL (`flexbox.rs:1936-2127`, e.g. `is_rtl_row = direction.is_row() && layout_direction.is_rtl()` at `1936`, and offset-origin flip at `2033-2036`), plus cross-axis reversal for column flex (`flexbox.rs:1779`). `compute/block.rs:348,1066-1075` mirrors margins/insets and remaps `TextAlign::Legacy{Left,Right,Center}` under `Direction::Rtl`. `compute/grid/{mod.rs:94-95, alignment.rs, placement.rs, implicit_grid.rs}` mirror grid placement and scrollbar-gutter side the same way. `compute/mod.rs:144-148` even mirrors the root node's own x-position.
- This is exercised by a large, browser-cross-checked fixture suite: `grep -rl 'Direction::Rtl\|"rtl"' ~/Projects/taffy/tests` matches 2275 files (re-verified; `grep -rl` counts matching files, not lines — the total matching-line count via `grep -rn ... | wc -l` is 9321) across `tests/xml/**/*_rtl.xml` and dedicated fixtures under `test_fixtures/{flex,block,grid}/*_direction_rtl.html`. This is materially more mature than "just `row-reverse`" — it is the real CSS `direction` property, implemented and tested across flex, block, and grid.
- akar does not use any of it today: `crates/akar-layout/src/lib.rs:1-10` re-exports `taffy::prelude::*` directly (no akar-owned `Style` wrapper), and every `Style { .. }` construction site found (`akar-layout/src/lib.rs:307,358,497,520`, plus every `*_layout()` function in `akar-components`) never sets `.direction`, so every node is implicitly `Direction::Ltr` (the struct default) today. **The capability is present and tested upstream; it is simply never invoked.**
- Practical implication for Task 2/6: akar should pass taffy's own `Direction` through as a real style property on relevant nodes rather than inventing a parallel mirror/post-process step in `akar-layout`. Reimplementing mirroring in akar-layout on top of taffy's already-correct implementation would be redundant, riskier (a second place to get flex/grid math wrong), and would fight taffy on every upgrade. The remaining work is ergonomic, not algorithmic: getting the right `Direction` value onto the right `Style` at construction time (see Task 6).

**Prior art is thinner than assumed, and both direction models differ from the epic's global-flag proposal in ways worth noting.**
- `~/Projects/egui`: `epaint::Direction` (`crates/epaint/src/direction.rs`) is a four-way cardinal enum (`LeftToRight | RightToLeft | TopDown | BottomUp`) used as `egui::Layout::main_dir` (`crates/egui/src/layout.rs:104,143,156-158`). It is a **per-`Ui`/per-container parameter the application passes explicitly** (`ui.with_layout(Layout::right_to_left(Align::TOP), ...)`), not a locale/script-driven global flag that mirrors an entire app automatically. egui does not appear to auto-detect RTL from text content or apply it tree-wide.
- egui's text cursor/selection code (`crates/egui/src/text_selection/text_cursor_state.rs`, `crates/epaint/src/text/cursor.rs`) has no `rtl`/bidi-aware arrow-key handling found by search — egui has the same "logical Left/Right key vs. visual direction" gap that akar has (see Task 5). This is useful context: akar would not be behind the closest immediate-mode reference on this specific sub-problem.
- `~/Projects/zed/crates/gpui`: no RTL/direction/writing-mode handling found anywhere in the crate (`Rtl`, `right_to_left`, `is_rtl`, `WritingMode` all zero matches). gpui is not a usable reference for this epic; it defers the problem entirely (or handles it upstream in a way not visible in this checkout).
- Mapping to akar's lifecycle (`DEVELOP.md` → Component lifecycle): egui's per-call `Layout` parameter doesn't map cleanly onto akar's construct/compute/paint split, because akar's `Style` is set once at construct time by `*_layout()` functions and reused across frames — there is no per-frame "layout call" to attach a direction argument to the way egui's immediate `with_layout` closures do. A context-level `AkarDirection`, read once by `*_layout()` functions at construct time (the same phase that already reads `&AkarTheme`), fits akar's existing "flat context, no cascade" model (`DEVELOP.md` → Theme system) much better than egui's per-call model. This confirms — with a concrete mechanism, not just an analogy — the epic's original hypothesis that a context-level flag is the right shape for v1.

**Component audit (Task 4 detail) revealed the actual codebase is a mix of already-neutral, easy-to-fix, and not-yet-existing surfaces** — narrower than the epic's original list of suspects. See Task 4 below for the full breakdown; headline finding: `akar-components/src/button.rs` and `badge.rs` currently have **no icon-slot concept at all** (`grep -n icon button.rs` returns nothing), so "icon placement in buttons/badges" from the epic's original Research list is aspirational, not an existing bug to fix. Likewise `scroll_area.rs` has no scrollbar thumb/track drawing code today (`grep -rl scrollbar akar-components/src` is empty) — "scrollbar side" is not yet an existing surface either.

**Text editing (Task 5 detail) has a confirmed, concrete, cited bug**, not just a hypothesized gap: `crates/akar-components/src/text_input.rs:128-135` and `textarea.rs:154-157` map `Key::Left` unconditionally to `previous_boundary` (decrease byte offset) and `Key::Right` unconditionally to `next_boundary` (increase byte offset). This is correct only because LTR text happens to have "visually left" and "logically previous" coincide. For pure-RTL text (where cosmic-text right-aligns the paragraph and reorders glyphs, per the bidi finding above), pressing the physical Left arrow key should move the caret to a smaller *visual x* — which is *logically forward* (toward `next_boundary`) for a right-aligned RTL line, not backward. `text_edit.rs`'s `previous_boundary`/`next_boundary` (lines 117-131) operate purely on the `&str` value with zero access to shaped-buffer bidi levels, so they structurally cannot make this distinction today — the fix needs a direction signal to reach `text_edit.rs`, not just a smarter string function.

### Task 2 — Survey taffy Direction Support

**Status:** Done

- Confirmed taffy has a first-class `Direction { Ltr, Rtl }` CSS-equivalent style property (`~/Projects/taffy/src/style/mod.rs:388-399`, field `CoreStyle::direction` at `mod.rs:448`, default `Ltr` at `mod.rs:595`) — distinct from `FlexDirection` (`Row`/`Column`/`RowReverse`/`ColumnReverse`, `style/flex.rs:108-126`), which the epic's original research note conflated it with ("row-reverse... is not the same as full logical-properties layout" — correct concern, but the epic assumed taffy lacked the logical-property layer; it does not).
- Confirmed it is wired into real compute logic, not just declared: flexbox main-axis reversal for `Row` (`compute/flexbox.rs:1936`, offset origin flip at `2033-2036`), cross-axis reversal for column flex (`flexbox.rs:1779`), block-layout inset/margin mirroring and `TextAlign::Legacy*` remapping (`compute/block.rs:348,1066-1075`), grid placement/justify mirroring and scrollbar-gutter side (`compute/grid/{mod.rs:94-95,alignment.rs,placement.rs,implicit_grid.rs}`), and even root-node x-position mirroring (`compute/mod.rs:144-148`).
- Confirmed this is exercised by an extensive, browser-cross-checked fixture/test suite: `grep -rl 'Direction::Rtl\|"rtl"' ~/Projects/taffy/tests` matches 2275 **files** (not lines — re-verified with `grep -rn ... | wc -l`, which counts 9321 matching lines across those files) across `tests/xml/**/*_rtl.xml` snapshot fixtures per layout mode, plus `test_fixtures/{flex,block,grid}/*_direction_rtl.html` source fixtures used to generate them.
- **Recommendation (answers the Task's core question directly): implement direction-aware layout as a taffy-level style property akar passes through, not a pre/post-processing mirror step in `akar-layout`.** Rationale:
  - Correctness: taffy's implementation is already tested against real browser layout output for flex, block, and grid RTL behavior. A parallel akar-side mirror pass would have to reimplement main/cross-axis reversal, inset mirroring, and justify-content mirroring correctly for every layout mode akar uses, essentially duplicating taffy's own logic with none of its test coverage.
  - Upgrade risk: a pass-through only needs a value on `Style` to keep working across taffy version bumps (per `DEVELOP.md`, taffy is a direct dependency read from `~/Projects/taffy`, not vendored) — a bespoke mirror step would need re-validating against taffy's internal axis/offset conventions on every upgrade, since it depends on details of taffy's *unmirrored* output (i.e., "invert this after taffy computes it") rather than a stable public API.
  - Complexity in `akar-layout`: `crates/akar-layout/src/lib.rs` currently re-exports `taffy::prelude::*` directly with no akar-owned `Style` wrapper (confirmed no `struct Style` or newtype in `akar-layout/src/lib.rs`). Pass-through requires no new type — only setting `.direction` on existing `Style { .. }` literals — versus a mirror step, which would need a new post-layout tree-walk that inverts every child's already-computed `Layout::rect` in world space, a strictly larger and more error-prone addition to `akar-layout`.
  - Confirmed gap this does *not* close: taffy's `Direction`-aware `TextAlign::Legacy*` remapping only fires in taffy's *block* layout mode (`compute/block.rs:1066-1075`). akar-components never uses taffy block layout — every construction site greped uses `Display::Flex` with `FlexDirection::Row`/`Column` (`akar-layout/src/lib.rs:307,358,497,520`). So taffy's own text-align mirroring is not reachable from akar's current layout usage; akar's *own* logical `TextAlign::Start/End` resolution in `paragraph.rs`, `heading.rs`, and `link.rs` (all three hardcode `TextAlign::End => rect[2] - text_width`, i.e. always "right", found at `paragraph.rs:56`, `link.rs:74`, `heading.rs:73`) needs its own direction-aware fix independent of taffy — see Task 4 and new Task 9.

### Task 5 — Text Input Caret/Selection Direction Prototype

**Status:** Partially Done (bug confirmed and localized via source analysis; no live render/prototype fix built — no GPU/display in this environment, and a real fix requires the direction plumbing proposed in Task 6, which is out of scope for research-only work)

- Confirmed the exact bug location by reading the Left/Right key handling in both editors:
  - `crates/akar-components/src/text_input.rs:128-135`:
    ```
    Key::Left if edit_state.has_selection() => edit_state.collapse_to_start(),
    Key::Left => edit_state.cursor = previous_boundary(value, edit_state.cursor),
    Key::Right if edit_state.has_selection() => edit_state.collapse_to_end(),
    Key::Right => edit_state.cursor = next_boundary(value, edit_state.cursor),
    ```
  - `crates/akar-components/src/textarea.rs:154-157` — identical pattern.
  - Both unconditionally treat `Key::Left` as "move to logically previous byte boundary" and `Key::Right` as "move to logically next byte boundary" (`previous_boundary`/`next_boundary`, `crates/akar-components/src/text_edit.rs:117-131`). This is correct *only* because LTR text has "visually left" and "logically previous" coincide.
- Reasoned from source (not rendered) what happens for a pure-RTL value: per the Task 1 finding, cosmic-text right-aligns an RTL paragraph and visually reorders its glyphs so the first logical character renders at the *right* edge. Pressing the physical Left arrow key is a request to move the caret to a smaller visual x — for a right-aligned RTL line that is a request to move *forward* through the string (toward `next_boundary`), not backward. Since `text_input.rs`/`textarea.rs` always call `previous_boundary` on `Key::Left`, the caret would move the wrong logical direction relative to what the user sees, for any pure-RTL or RTL-dominant value. This conclusion is inferred from the confirmed alignment/shaping behavior (Task 1) and the confirmed key-handling code, not from an actual screenshot — flagged as source-analysis-based per this task's instructions.
- Root cause, precisely localized: `crates/akar-components/src/text_edit.rs` is entirely string-only — `previous_boundary`/`next_boundary` (`text_edit.rs:117-131`) take `&str` and a byte position and know nothing about how that string was shaped or which direction it visually reads. They have no access to the `glyphon::Buffer` or its per-glyph `level` (bidi embedding level) that `crates/akar-core/src/text_pipeline.rs` already computes and uses for caret geometry (`caret_x`/`glyph_boundary_x`, lines 332-379). **The caret's rendered *position* is already bidi-aware (via `TextPipeline::geometry`); the caret's *movement logic* on arrow keys is not, and lives in a different crate (`akar-components` vs. `akar-core`) with no shared access to bidi levels.** This is the concrete architectural gap a fix needs to close — see new Task 10 below.
- No prototype fix or before/after screenshots were produced in this pass: a *correct* fix needs a direction signal (at minimum, paragraph-level RTL/LTR) to reach `text_edit.rs`'s boundary functions, which does not exist anywhere in `akar-components` or `akar-core` today (confirmed by grep — no `Direction`/`Rtl` type exists outside `akar_core::text_pipeline`'s internal use of cosmic-text's `glyph.level`). Building even a minimal prototype would mean partially implementing the Task 6 proposal, which this research pass is scoped not to do. Recorded as new Task 10 (concrete, implementable) instead.

### Task 6 — Scope Proposal for First Implementation Pass

**Status:** Done

Based on Tasks 1-5, this is a concrete proposal for the first implementation pass, following akar's existing conventions (context-level flat config, no cascade, per `DEVELOP.md` → Theme system; construct/compute/paint separation).

**1. `AkarDirection` type and where it lives.**
- Add `pub enum AkarDirection { Ltr, Rtl }` (mirroring `taffy::style::Direction`'s two variants, but as an akar-owned type so `akar-layout`/`akar-components` don't leak `taffy::Direction` across the C ABI boundary — the same reasoning epic 020 used for its akar-owned `FontFamily`/`FontWeight`/`TextAlign`/`TextStyle` types wrapping glyphon internals, so public component APIs never expose glyphon types directly, per `epics/020-component-webpage-sample.md` Task 2 and Design Decisions). **Correction:** an earlier draft of this section cited these as "`AkarTypography`" — no such type exists; `epics/022-font-support.md`'s own Task 1 findings (line 63) already caught and corrected this exact naming error for a different epic, and this draft had reintroduced it. The real types live in `crates/akar-components/src/text_style.rs`. Natural home for `AkarDirection`: `crates/akar-layout/src/lib.rs`, next to `AkarNodeContext` (`lib.rs:18-31`), since it's consumed at `Style` construction time.
- Store the active direction on `Layout` itself (`crates/akar-layout/src/lib.rs:34-39`), as a new field parallel to `screen_origin`/`namespace_id`, with `set_direction`/`direction()` accessors mirroring the existing `set_namespace_id`/`namespace_id()` pattern (`lib.rs:57-63`). Rationale, established in Task 3: every `*_layout()` construction function already takes `&mut Layout`, but not every one uses `&AkarTheme` meaningfully (e.g. `navbar_layout`'s `_theme` parameter is unused, `navbar.rs:32`) — anchoring direction to `Layout` guarantees it's available wherever a `Style` is constructed, without depending on theme plumbing that isn't uniformly used for other purposes. `AkarCore` (`crates/akar-core/src/context.rs:8-21`) is the wrong home for a layout-tree-scoped value — `Layout` and `AkarCore` are separate objects (per the crate boundary table in `AGENTS.md`: `akar-layout` owns the taffy wrapper, `akar-core` owns draw list/input), and `Layout` already carries the other per-tree context (`screen_origin`, `namespace_id`) that direction most resembles.
- Applications set it once via `layout.set_direction(AkarDirection::Rtl)`, analogous to how `text_edit_keybindings` is configured once on `AkarCore` in epic 018 (`epics/018-text-editing-keybindings-and-clipboard.md`'s "Context-Level Keybinding Defaults").

**2. Where it plugs into `akar-layout`.**
- `*_layout()` construction functions (`navbar_layout`, `card_layout`, future `heading_layout`, etc. — per `DEVELOP.md`'s construct/compute/paint model) read `layout.direction()` and set `taffy::Style { direction: direction.into(), ..existing }` on the nodes they construct — a direct `From<AkarDirection> for taffy::style::Direction` impl, no reimplementation of taffy's mirroring logic (per the Task 2 recommendation). This is additive: existing `Style { .. }` literals gain one field.
- Do **not** attempt to retrofit every existing `Style` construction site in one pass — scope the first implementation to the specific nodes exercised by the two proof components below (Task 6 §4), and leave the rest at the `Direction::Ltr` default until proven.

**3. Where it plugs into text editing (`TextEditState` / shared editing engine).**
- `crates/akar-components/src/text_edit.rs`'s `previous_boundary`/`next_boundary` (lines 117-131) need a direction parameter to choose which byte-offset function corresponds to "visually toward smaller x" vs. "visually toward larger x" for a given paragraph. Minimal viable signature change: `pub fn visual_previous(value: &str, position: usize, direction: AkarDirection) -> usize` / `visual_next(...)` that, for v1, treat the *whole value* as one paragraph-level direction (matching this epic's own "global direction, not mixed/per-run" scoping — see Notes for Future Work) — i.e. under `AkarDirection::Rtl`, `visual_previous` calls today's `next_boundary` internally and vice versa. This avoids needing shaped-buffer/bidi-level access inside `akar-components` for v1; true per-run mixed-direction caret movement (reading `TextPipeline`'s per-glyph `level`, as `caret_x`/`glyph_boundary_x` already do in `crates/akar-core/src/text_pipeline.rs:332-379`) is an explicit deferral (§5).
- `text_input.rs:128-135` and `textarea.rs:154-157` change their `Key::Left`/`Key::Right` arms to call `visual_previous`/`visual_next` with a direction obtained from the component's `&Layout` (`layout.direction()`) rather than the current unconditional `previous_boundary`/`next_boundary`.
- `TextEditState` itself (`text_edit.rs:1-5`, `cursor`/`anchor` as byte offsets) does **not** need to change shape — direction only changes which boundary function callers invoke, not the state representation. This keeps the change additive and low-risk against epic 018's existing test suite (`text_edit.rs`'s `#[cfg(test)]` module, ~280 lines of coverage).

**4. Proof components for the first pass (deliberately small).**
- **`navbar.rs`**: per Task 4, its `start`/`center`/`end` slots use plain `FlexDirection::Row` with no hardcoded pixel math — wiring `layout.direction()` into `navbar_layout`'s `Style` construction (`navbar.rs:34-45`) should demonstrate taffy's own Row-reversal (Task 2 finding) with **zero paint-time code changes**. This proves the `Layout`→taffy plumbing end-to-end with minimum component-side risk.
- **`text_input`**: per Task 5, wiring `visual_previous`/`visual_next` proves the direction model extends past pure layout into interaction/caret semantics, the epic's stated highest-value target.
- Excluded from the first pass on purpose: `textarea` (same fix as `text_input`, but defer to reduce first-pass surface — apply once `text_input`'s approach is validated), `alert.rs` (needs the larger raw-pixel-math rewrite from Task 4, not just a flag), `paragraph.rs`/`heading.rs`/`link.rs` `TextAlign::End` fix (small but independent of the caret/layout proof — good second-wave candidate, see new Task 9).

**5. Explicit deferrals (out of scope for the first implementation pass):**
- Per-node/mixed-direction documents (a paragraph or subtree with its own direction independent of the app-wide setting) — `AkarDirection` is a single context-level (`Layout`-level) value for v1, not a per-`NodeId` property. Confirmed consistent with the epic's own original Research bullet on this.
- Full icon/scrollbar mirroring across all 30+ components — moot for icons/scrollbar specifically today per Task 4 (neither surface exists yet in the codebase), but also true in general: only `navbar` and `text_input` are in scope for the first pass.
- `alert.rs`'s raw pixel-math mirroring (Task 4) — larger, more error-prone rewrite; defer to a follow-up once the `Layout`-level direction plumbing is proven on simpler components.
- `paragraph.rs`/`heading.rs`/`link.rs` `TextAlign::Start`/`End` direction-aware resolution (Task 2/4) — small and independent; good second-wave task once `AkarDirection` exists (new Task 9 captures this precisely).
- Per-run/mixed-direction caret movement using `TextPipeline`'s per-glyph bidi `level` (as opposed to whole-value paragraph-level direction) — deferred per §3 above; the epic's own scoping note already flags mixed-direction documents as a larger effort.
- Vertical writing modes (CJK vertical text) — explicitly out of scope per the epic's existing Notes for Future Work, unrelated to RTL.
- Canvas world-space text (`CanvasPainter`) — per the epic's existing Notes for Future Work, canvas text is display-only and bypasses `akar-layout` entirely, so it needs its own direction handling pass (or an explicit "not supported yet" decision) independent of this `Layout`-based plumbing. Not addressed by this proposal.
- C ABI exposure of `AkarDirection`/`akar_layout_set_direction` — natural to add (mirrors `akar_set_text_edit_keybindings` from epic 018) but not required to prove the Rust-side model first; recorded as new Task 12 rather than folded into the initial proof.
- Selection-drag (pointer) direction-awareness — Task 5's original scope mentioned "selection-drag" behavior; source analysis for this pass focused on keyboard Left/Right (the clearer, more isolated bug). Pointer-drag selection direction correctness is a related but separate follow-up once keyboard caret movement is fixed, since it likely reuses the same `visual_previous`/`visual_next`-adjacent geometry-to-offset mapping — captured in new Task 11.
